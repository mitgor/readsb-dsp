Four-part Stream1090 latency optimization

10 November 2026, Europe/Berlin. Implemented by four subagents, integrated and tested on Mac and Raspberry Pi 5 Model B Rev 1.0. Production unchanged.

The new path shares complete upstream energy candidates, uses persistent Rust stock/admission indexes, wakes on actual producer completion and retries pending cold-start slices when new causal evidence arrives. The same 20 ms native decoder, 50 ms energy algorithm, trust resets, CRC/identity/conflict/alignment checks and shared five-second Rust final transmission history remain in place.

The paired Pi medians improved from 957/571 ms to 189/151 ms, retaining 79/79 transmissions in each trial. The sub-250 ms tail target is not consistently met: optimized p95 was 488 ms and 250 ms, with 52/79 and 75/79 packets under 250 ms. There is very little margin beneath the 35%-of-one-core quota; supervisor health monitoring also consumes CPU outside the measured benchmark child. This is a promising isolated implementation, not a proven production latency guarantee.

CPU and honest shared-compute accounting

All upstream energy computation is included once in each measured total. The sharing adapter performs no RF decoding; it receives full pre-admission energy completions from the unchanged test producer. Consumer CPU is total minus that upstream energy thread's CPU; it is a subtotal, not the complete system cost. The benchmark does not connect to the live production publisher or measure a full-system saving from eliminating an actually running duplicate producer.

Validation and limits

Native admission passed 333 exact Python/Rust comparisons across 14 control groups, including 176 historical actual-RF energy/deferred all-source checks. Sharing has 13 controls, completion bridge 22 Python/native controls and cold retry 14 controls. Tests cover future-evidence rejection, bounds/epochs, CRC/identity/conflicts, quarter ticks, source priorities, stock eviction, stale cache evidence, idle drains, pending retries and final fallback. The incremental decoder itself was unchanged; its earlier boundary/deadline/noise/sanitizer regressions still apply.

Raw native and energy outputs match exactly between Mac and Pi in all trials; original stock bytes and order are preserved. Detailed parity checks are in summary.json. All packet payloads and raw decoder timestamps match. In the admitted Pi output, 10 of 158 paired timestamps differ by one 12 MHz tick (83 ns) because clock calibration uses earlier causal evidence. The remaining 148 match exactly. All transmissions remain matched within the unchanged 120 us tolerance. Original stock DF17 bytes/order are preserved in every condition. The fixture did not retain all other stock message types. All candidate outputs remain quarantined and are never training labels or feeder input. No receiver/feeder/relay/collection service was restarted. Models/gain/routes/switches and the 5,000,000,000-byte RF cap are unchanged. Protected target state unchanged: True.

An initial harness erroneously tested NativeAdmission truthiness by its empty stock length, selecting the legacy bridge. That Mac result is preserved as invalid for the optimized condition. An explicit engine/bridge assertion now prevents this; the setup-only Pi unit was stopped before RF replay, with source and logs retained. Final results use all four components, including shared input accounting and completion/retry counters, verified explicitly.

The live native guard had already restored the executable at 16:37 UTC before this work after a primary sample-loss counter increase. This experiment leaves that fallback intact; it neither reactivates native inference nor attributes that older counter event to a particular cause.

Deployment gate

Nothing was deployed. Judge latency using the actual Pi rows above, not the Mac result. Before enabling this path, collect longer untouched RF with actual tap arrival/completion times and adequate distant opportunities, validate sustained queues/retention against the complete enabled pipeline, and retain the existing fallback. Component correctness and a short engineering replay do not establish production latency or range performance.
